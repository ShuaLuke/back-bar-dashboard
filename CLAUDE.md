# Project notes

Static, single-page dashboard. No framework, no bundler. D3 v7.8.5 is loaded from cdnjs.

- Edit `src/template.html` (menu dashboard) or `src/costmodel.js` / `src/costtool.js` / `src/sample.js` / `src/xlsx-lite.js` (the Cost & sales tool), then run `python3 scripts/build.py --offline` to regenerate `index.html` and `dist/offline/index.html`. Never edit `index.html` by hand. build.py inlines the four `src/*.js` files at the `__COSTMODEL__`, `__SAMPLE__`, `__XLSX__`, `__COSTTOOL__` markers (engine, sample and xlsx before the main script; the tool after it) and fills `__D3_SRI__` and `__CSP__` from `vendor/manifest.json` (run `scripts/vendor.py` once to create it). Run `node --test tests/*.test.js` after touching the engine.
- Data changes: edit `data/drinks_raw.tsv` (columns: group, restaurant, section, drink, price, ingredients; price may be blank), then run `scripts/normalize.py` before building. Add a rule to `RULES` in normalize.py for any new ingredient wording; rule order matters (liqueur rules before fruit rules, so "peach liqueur" isn't "Peach"). The script fails loudly on unmapped ingredients. After changing rules, diff the José Andrés mappings before/after to catch regressions. `data/sources.md` records each menu URL and read date; keep it current.
- Multiple restaurant groups: `GROUPS`, `REST_GROUP`, `gShort()` and `HOME` (the first group, José Andrés) in the template. The sidebar filters by group or restaurant and starts with only `HOME` (José Andrés) selected, by request; ops views use the selected restaurants; the Compare groups view (`renderGroups`) always uses every group. Zero-proof is detected from the section name (`ZERO_SECTION` in normalize.py).
- Each drink in drinks.json has `ings` (deduped canonical ingredients with `cat`) and `parts` (every menu ingredient line as `[raw, canonical]`, used for display).
- Categories (`cat`) roll up to 9 families via `CAT2FAM` in the template. Family colors are the `--f-*` CSS tokens.
- Light theme only, by design. Brand: "Well & Call" (bar slang: a well drink is the house pour, a call drink names the brand; the repo keeps its original `back-bar-dashboard` name so the Pages URL stays put), aperitivo orange `--accent`, teal `--teal`, fonts Geist + Geist Mono.
- Main JS entry points: `render()` re-renders everything on filter change; `setView(name)` switches views (`overview`, `ingredients`, `matrix`, `map`, `prep`, `price`, `gaps`, `groups`, `h2h`, `costs`, `about`). `renderChord`, `renderOps`, `renderOverview`, `renderGroups`, `renderH2H` and `renderCosts` each own one view. `h2h` compares two entities (`r:<restaurant>` or `g:<group>` ids, stored in `h2h` / localStorage `ja-h2h`).
- `og.png` (link preview, 1200x630) is rendered by `scripts/make_og.py` from `src/og-card.html` plus a headless screenshot of the built page opened on Head to head (first group vs third, i.e. José Andrés vs STARR; see the `hook` in make_og.py). Re-run it after visible Overview or data changes. og:image URLs point at https://shualuke.github.io/back-bar-dashboard/.
- Template content above `<!--BODY-->` is emitted into `<head>` by build.py.
- Tooltips: give any element `data-tip="<html>"` (use `tipAttr()`, `ttRows()`, `ttList()`). One delegated handler does hover on desktop, tap-to-show / tap-again-to-open on touch, and focus for keyboard.
- The `costs` view is the Cost & sales tool, ported from the CAVA sibling (`../cava-dashboard`) and adapted to bars. `renderCosts()` in the template is a stub; `src/costtool.js` renders into `#cost-out` itself (state object `CT`, one delegated click/change handler with `data-act` / `data-set` attributes, `render()` rebuilds the tab), ignores the sidebar filters, and boots the sample dataset lazily when the view is first shown. The tool is organized by job (`CT.job`: home, advise, review, menu, price, ideas, explore, data); the guided flows keep their own state in `CT.flow.*` and build a scenario object for `analyze` (`pcScn()`, `mcScn()`); `resultsFor(scope, scn)` caches analyses per scope; Explore holds the five original tab renderers (`tabCosts` … `tabRecon`) behind the scope bar. Explanations: wrap any figure in `X(value, {l, f, v, src, asm})` (formula, values, source, assumption flag), give each step one `reading(...)` line, and mark user-set parameters with `asmBadge(...)`. `src/costmodel.js` (`CostModel`) is pure, dependency-free and shared with Node: `TEMPLATES` is the data dictionary (keep `docs/data-dictionary.md` in sync via `node scripts/make_sample.js`), `validate` → `build` → `analyze(M, scope, scenario)` returns one results object `R` the views read; `decompose`, `suggest`, `recommend`, `addComponent`, `RECON` and `SELFTEST` as in the CAVA repo. Bar vocabulary in the files: ingredients (bottles) with `bottle_cost/size/unit`, `pour_size/unit`, `yield_pct`, `upcharge` (a call brand is its own row), `abv_pct`; drinks with `section` and `custom = 1` for the well & call drink built from modifiers; recipes with `qty` + optional `unit` (converted to pours via `toPours`); sales/modifiers/restaurants/extras/waste/actuals/inventory (counts in bottles convert via `pourPerUnit`). Engine internals keep the CAVA names (`M.comps`, `M.drinks`, `it.byo`, `it.addon` = food line, `c.station`→`category`, `fam` via `CAT_FAM`, `M.pkg` = extras, `M.wellCost(category)` = the well a called spirit replaces). Food lines (`FOOD_LINE` sections) are never costed and never in beverage revenue; a called spirit on a menu drink replaces the spec's spirit of the same category (`applyMods`). `R.strength` (standard drinks from ABV) replaces the CAVA nutrition check; `RECON` pass band is 0–4 pts. `src/sample.js` (`SampleData.makeSample({drinks, catFam})`) is the seeded synthetic dataset for Oyamel, Jaleo and Zaytinya; every parameter is documented in `docs/sample-data.md`. Keep every sample number labeled as synthetic, never as real costs or sales. `docs/methodology.md` must describe every formula in the engine; update both together. Security posture of the page is part of the product: a CSP with `connect-src 'none'` (set in build.py), SRI on the D3 script, no fetch/XHR anywhere, storage only behind the opt-in (`ja-ct-persist`, IndexedDB `ja-costtool`, localStorage `ja-ct-saved`). Don't add network calls or third-party scripts; `docs/security-review.md` lists every request and must stay true.
- Detail views share one renderer, `renderInspect(box, ds, S, target, nav, opts)`, for ingredient / pair / category targets. It's used by the pairing map panel, the matrix panel (`renderPair`) and the overview drawer (`openDrawer`). Each caller passes `nav(target)` to decide what clicks do. Click rule: ingredients, pairs and categories open detail (the drawer on the Overview); summaries (restaurant rows, signals, "→" links) go to their page.
- Sub-map drawing helpers: `subMap()` (two-column links), `fanMap()` (one node to many, grouped by category: ingredient partners, or what else is in a pair's drinks) and `subChord()` (within one category), wired by `wireSubMap()`.
- Guided tour: `TOUR` steps (view + target selector + copy) with `tourStart()`; auto-starts once per browser (`ja-tour-done`), replay via the sidebar's Take a tour. `window.__notour` suppresses it (make_og.py sets it so the share image stays clean). Update the steps when views are added or renamed.
- The Overview's "Worth a look" card ends with a Cost & sales signal fed by `window.ctSummary()` from the tool (`costSignal()` in the template); the tool calls the dashboard's `render()` once after its sample boots so the signal appears.
- Overview must fit one desktop screen (no page scroll) at 1280×720 and up; check this after layout changes.
- Neighborhood Restaurant Group covers ChurchKey, The Sovereign and Iron Gate only: Bluejacket's cocktail menu isn't published online and Birch & Barley closed in 2024 (now Mallard).
- Good next steps: split the template into css/js modules, add Vite, add a monthly menu re-scrape to track changes; for the tool, batch (pre-mixed) recipes costed as ingredients, bottle-level par and ordering suggestions, a screen-reader pass and reading files from an internal URL.
